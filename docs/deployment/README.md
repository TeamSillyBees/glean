# 部署说明

Glean 由 Go API、Web、PostgreSQL 和 Redis 组成。镜像发布与服务器部署相互独立；采集调度和模型调用默认关闭。

## 选择对应部署方式

| 场景                  | 入口                                | 布局                                                                     |
| --------------------- | ----------------------------------- | ------------------------------------------------------------------------ |
| 维护现有线上实例      | [当前实例](current-instance.md)     | `/root/docker/glean/compose.yaml` 管理四个服务，Web 容器终止 HTTPS       |
| 发布并验证新镜像      | [GitHub Actions](github-actions.md) | 独立手动工作流，按提交构建并按 digest 验证，不访问服务器                 |
| 使用仓库发布/备份工具 | [发布工具](release-tools.md)        | `releases/state/ops.env` 布局，外置 PostgreSQL / Redis 与宿主 HTTPS 代理 |
| 本地开发或容器验证    | [开发指南](../development.md)       | 根目录 Compose 与本地配置                                                |

**仓库 `deploy.yml` 和 `scripts/production` 尚未适配当前线上单 Compose 布局。** 现有实例的服务器部署开关保持关闭；不能直接对它启用旧工作流或运行旧发布/恢复脚本。统一布局是 [Roadmap](../roadmap.md) 的首要运维事项。

## 上线流程

1. **准备依赖和配置。** 使用受限数据库角色、PostgreSQL `verify-full`、受限网络中的认证 Redis、HTTPS、明确 CORS 白名单和可信代理，关闭匿名 API 文档。每个运行实例分配唯一 Snowflake node。
2. **初始化或升级数据库。** 新实例显式执行迁移、首次管理员 seed 和可选基线导入；既有实例只应用待执行迁移，保留现有账号和凭据。
3. **验证并发布镜像。** 等待目标 main 提交的完整 CI 成功，手动发布镜像，使用独立 runner 验证后的不可变 digest。
4. **备份并切换。** 记录旧镜像和数据库版本，停止全部写入者，完成对应布局的数据库、Redis、配置和文件备份，再迁移和切换。校验和通过不能代替恢复演练。
5. **检查服务。** 核对后端 `/ready`、Web `/healthz`、HTTPS、登录与退出、论文和主题数量、来源证据、权限和持久数据。
6. **按需启用后台能力。** 先做有界真实采集验收；确认查询范围、操作员、限流与预算后启用调度。模型端点、密钥和费用预算单独配置。

具体命令与失败恢复语义遵循所选布局的手册，不混用两套目录和脚本。

## 后台开关

| 配置                                 | 含义                                                  |
| ------------------------------------ | ----------------------------------------------------- |
| `INITRA_MONITOR_OPERATOR_ID`         | 已有启用账号的审计操作员 ID                           |
| `INITRA_MONITOR_SCHEDULER_ENABLED`   | 采集主开关；装配所需 worker/scheduler，按持久计划推进 |
| `INITRA_MONITOR_MODELS_ENABLED`      | 独立模型处理开关                                      |
| `INITRA_MONITOR_MODELS_AUTO_DISPLAY` | 机器结果展示开关，不等于人工纳入                      |

修改 env 文件后须按对应 Compose 配置重建后端容器，单纯 `docker compose restart` 不会重新加载 env_file。启用模型后，已有待配置候选可能继续处理，先检查积压、历史回溯范围和累计预算。详见[论文处理](../guides/paper-pipeline.md)。

## 日常运维

- 检查服务健康、证书到期、磁盘和备份可恢复性；数据库证书与公网 HTTPS 证书分别管理。
- 在“采集状态”检查实际成功时间、覆盖范围、失败和隔离数量。页面刷新只读取状态；管理员的连通性按钮才发起轻量外部探测。
- 备份保留期限、周期执行、异机副本和恢复目标需明确配置；当前实例的完成情况见其运维记录。
- 回退前确认数据库 schema 与旧应用兼容。应用镜像回退不自动回退数据库；恢复到独立空库验证后再决定切换。

API 与权限说明见[认证与权限](../reference/security.md)，安全报告渠道见 [SECURITY.md](../../SECURITY.md)。
